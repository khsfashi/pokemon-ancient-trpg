# P1 External Source Registry

Last verified: **2026-08-14**

This is the durable P1 registry required by `docs/REFERENCE_PROTOCOL.md`. It records what an external source is useful for, what it actually exposes, what license/provenance boundaries are known, how it must be pinned, and whether this project should `ADOPT`, `ADAPT`, `REJECT`, `DEFER`, or `REVISIT IN P6` it.

This registry is evidence for later contracts. It is **not** permission to silently convert community data into Pokémon canon, copy third-party assets, or freeze design-dependent production choices before their owning phase.

## Registry contract

Every substantive source record must include:

- stable source ID,
- source/project name and canonical URL,
- verification date and evidence anchors,
- intended project purpose,
- exact data/resource/behavior classes available,
- license/provenance relevant to the intended use,
- Pokémon-IP caveat where applicable,
- update/version/pinning strategy,
- risks and known incompleteness,
- `ADOPT / ADAPT / REJECT / DEFER / REVISIT IN P6` decision,
- owning downstream contract or phase.

When a repository has both code/data and Pokémon images/audio, those rights boundaries must be recorded separately. A repository-level open-source license does not automatically relicense underlying Pokémon intellectual property.

## Source-role policy

No single community source is treated as universally authoritative.

Current P1 direction:

1. **Official Pokémon / Nintendo / rights-holder material** wins for official policy statements and setting/canon claims when such a source exists.
2. **PokéAPI static data** is the preferred structured baseline for broad species/form/game metadata because it exposes a stable, machine-readable REST-shaped dataset and schema.
3. **Pokémon Showdown** is a complementary source for generation-specific battle mechanics, learnset/legality behavior, and simulator-oriented move/ability semantics.
4. Conflicts between community sources are recorded and resolved intentionally in the owning design/data phase; fields must not be silently merged just because both sources expose similarly named values.
5. Production runtime must not depend on either remote service by default. Later import tooling should pin an upstream revision, normalize only approved fields into project-owned artifacts, validate them, then build runtime indexes/caches.

P1 intentionally does **not** define project-owned threat ratings, ecology tags, bond difficulty, local folklore, encounter rarity, or other derived gameplay semantics. Those belong to P4/P5 after P2/P3 constraints exist.

## SRC-DATA-001 — PokéAPI `api-data`

**Decision:** `ADAPT`  
**Role:** preferred broad structured Pokémon data baseline  
**Canonical repository:** https://github.com/PokeAPI/api-data  
**Official API documentation:** https://pokeapi.co/docs/v2  
**Verified revision:** `2cda0b56a3a8ad2529d8aac73528225f96d2c848` (2026-08-11 updater regeneration)  
**Verified:** 2026-08-14

### Evidence anchors

- `api-data` README: static JSON copy of PokéAPI plus generated JSON Schema and an updater bot.
- `api-data/LICENSE.txt`: BSD 3-Clause text, copyright PokéAPI contributors.
- PokéAPI v2 docs: `pokemon`, `pokemon-species`, `move`, `generation`, `pokedex`, `version`, `version-group`, locations/encounters, abilities, evolution and related resource classes.

### Useful data classes

At reconnaissance depth this source can provide or link:

- Pokémon instances/varieties and species relationships,
- national/source identifiers and names,
- forms/varieties,
- base stats,
- type slots including historical type data,
- abilities including historical ability data,
- move associations with learn method / level / version-group detail,
- move metadata and historical values,
- generations, versions and version groups,
- Pokédex membership,
- evolution chains,
- encounter/location data,
- species metadata such as color, shape, growth rate, egg groups, capture rate and habitat where populated,
- sprite and cry references exposed by the API data model.

The existence of a field does not mean this project will import or expose it. P4 owns the canonical-source → project-domain mapping.

### License / provenance boundary

The `api-data` repository carries the BSD 3-Clause license from PokéAPI contributors. Treat that license as applying to rights the PokéAPI contributors can grant in the repository materials.

Pokémon names, game-derived facts, characters, designs, artwork, audio, trademarks and other franchise IP remain a separate rights question. Do not record `BSD-3-Clause = Pokémon IP licensed`.

Sprite/cry URLs or resource identifiers contained in structured data are **references**, not proof that the linked asset may be redistributed by this repository.

### Update and pinning strategy

- Upstream data is regenerated by an updater bot, so `master` is intentionally moving.
- Any importer must pin an exact commit or content hash rather than consuming `master` implicitly.
- The pinned revision and import timestamp must be stored with generated project artifacts.
- Updating the pin must be an explicit data update with validation/diff evidence, not an invisible runtime change.
- Runtime remote calls to `pokeapi.co` are rejected by default unless P7 later proves a concrete need.

### Risks / incompleteness

- Community-maintained extracted data, not a rights-holder canonical database.
- Some fields are version-sensitive and must retain generation/version-group context.
- Habitat and other descriptive fields may be null/incomplete or unsuitable as direct ecology rules.
- Flavor text is copyrighted game text and should not be copied wholesale into project-authored narrative merely because the API exposes it.
- Resource URLs cross into separate image/audio provenance concerns.

### Downstream ownership

- **P4:** decide the exact canonical fields imported and define project-owned derived Pokémon fields.
- **P6:** classify any referenced visual/audio resources separately.
- **P7:** implement pinned import, validation, generated artifacts and cached runtime indexes.

## SRC-DATA-002 — Pokémon Showdown server / Dex data

**Decision:** `ADAPT`  
**Role:** complementary battle-mechanics, learnset and generation-specific rules evidence  
**Canonical repository:** https://github.com/smogon/pokemon-showdown  
**Dex documentation:** https://github.com/smogon/pokemon-showdown/blob/master/sim/DEX.md  
**Verified revision:** `4f3615ac579cb72fa59919bc34d77ae6542c1c94` (2026-08-12)  
**Verified:** 2026-08-14

### Evidence anchors

- Repository README: Pokémon Showdown server is distributed under the MIT License and can be used as a JavaScript library for battle simulation / Pokédex data.
- `LICENSE`: MIT License, copyright 2011-2026 Guangcong Luo and contributors.
- `sim/DEX.md`: Dex exposes Pokémon, moves, items, abilities, natures and stats; `Dex.mod(...)` provides other-generation views.
- `sim/DEX.md` explicitly warns that Dex includes nonstandard data and that return values are not stabilized, recommending a pinned dependency version.
- Simulator validation/data files encode obtainability, move legality and generation-specific rules.

### Useful data / behavior classes

- species/form records,
- moves and detailed move behavior used by the simulator,
- abilities,
- items,
- natures and stats,
- generation-specific mods via `Dex.mod`,
- learnsets / move-source information,
- obtainability and legality behavior,
- generation-specific simulator mechanics useful for research or cross-checking.

### License / provenance boundary

The server repository is MIT-licensed as software and associated repository material to the extent contributors can license it.

That does not make Pokémon names, characters, designs, game text, audio, sprites or other underlying Pokémon IP MIT-licensed. Pokémon Showdown is also a community simulator, not an official Pokémon data authority.

Do not copy simulator implementation wholesale merely to obtain a few facts that can be normalized into a smaller project-owned contract.

### Update and pinning strategy

- Pin an exact Git commit or released package version for every extraction/analysis run.
- Do not depend on unversioned `master` at runtime.
- Preserve the upstream revision beside generated normalized artifacts.
- Explicitly filter/flag nonstandard content before ingesting anything into project-owned data.
- Because Dex return values are documented as unstable, importer code must validate expected shapes against the pinned revision rather than assuming an evergreen API contract.

### Source-selection rule

Use Showdown primarily where its specialization is valuable:

- generation-specific move/ability mechanics,
- learnset/legality evidence,
- differences across battle generations,
- simulator behavior that needs deterministic cross-checking.

Do **not** automatically prefer it over PokéAPI for every species metadata field. When both sources expose the same category, P4 must choose one authoritative project input or define a deliberate cross-check rule.

### Risks / incompleteness

- Includes CAP, custom, unreleased/past and other nonstandard data unless filtered.
- Simulator implementation may contain competitive/community interpretations or implementation details irrelevant to this text TRPG.
- Exact main-series fidelity is a research target of the simulator, but the repository is not an official Pokémon source.
- Pulling the full simulator into production would add unnecessary surface area if only normalized source data is needed.

### Downstream ownership

- **P4:** choose which move/ability/learnset/mechanics facts, if any, become canonical inputs for the project.
- **P7:** implement only the minimum pinned extraction/import path justified by P4; do not make the whole simulator a runtime dependency without evidence.

## SRC-ASSET-001 — PokéAPI `sprites`

**Decision:** `REVISIT IN P6`  
**Role:** high-coverage Pokémon sprite/icon source candidate; provenance risk requires second-pass selection  
**Canonical repository:** https://github.com/PokeAPI/sprites  
**Verified revision:** `c10459b9b0129eaca5c5d9b1cac65336debb1d08` (2026-08-08)  
**Verified:** 2026-08-14

### Evidence anchors

- README: repository hosts many Pokémon sprites, with version-organized front/back/shiny/female variants, icons, animated GIFs, official artwork/Home assets, Showdown community sprites and item images.
- `LICENCE.txt` starts by stating that all image contents are copyright The Pokémon Company, then states that the repository is distributed under CC0 1.0 Universal.
- The same CC0 text limits the waiver/license to rights the affirmer owns and disclaims responsibility for clearing third-party rights.
- README separately credits Smogon/community-created sprite work for some assets.

### Resource coverage

Useful candidate classes include:

- default Pokémon front/back sprites,
- shiny and gender variants where available,
- generation/game-specific sprite sets,
- animated sprite variants for selected generations,
- party/icon-style images for selected generations,
- official-artwork/Home-style images,
- Showdown-community sprite variants,
- item images.

Coverage and dimensions vary by generation and source family, so P6 must choose an intentionally small subset rather than assume one uniform asset contract.

### License / provenance boundary

This repository is a clear example of why repository license and underlying asset rights must be separated.

The repository license text itself says the image contents are copyright The Pokémon Company. Therefore the CC0 declaration must **not** be interpreted by this project as proof that Pokémon images are cleared for unrestricted redistribution.

Community-created sprites add a second provenance layer: contributor/community permission may exist for some works, while the depicted Pokémon designs remain franchise IP.

### P1 policy

- Do not vendor or mass-copy this sprite corpus into `pokemon-ancient-trpg` during P1.
- Do not treat a raw GitHub URL as a production redistribution policy.
- It is acceptable to retain the source as a P6 candidate and to study its file organization/coverage.
- Any temporary research fixture should avoid committing a large asset set and must remain clearly non-authoritative.

### P6 revisit questions

P6 must decide, after P2-P5:

- whether the game actually needs Pokémon sprites/icons and at what presentation density,
- which exact sprite family/generation/style is coherent with the approved world presentation,
- whether selected files may be bundled, should be user-fetched at build time, or should be omitted,
- attribution/provenance requirements for any community-created subset,
- stable resource-ID mapping from species/forms to files,
- preprocessing/dimensions/formats and mobile decoded-memory/loading budgets.

### Downstream ownership

- **P6:** authoritative asset selection, redistribution/fetch/generation policy, manifests, preprocessing and mobile budget.
- **P7:** implement only the P6-approved resource pipeline.
