# P1 External Source Registry

Last verified: **2026-08-14**

This is the durable P1 registry required by `docs/REFERENCE_PROTOCOL.md`. It records what an external source is useful for, what it actually exposes, what license/provenance boundaries are known, how it must be pinned, and whether this project should `ADOPT`, `ADAPT`, `REJECT`, `DEFER`, or `REVISIT IN P6` it.

This registry is evidence for later contracts. It is **not** permission to silently convert community data into Pokémon canon, copy third-party assets, or freeze design-dependent production choices before their owning phase.

## Registry contract

Every substantive source record must include:

- stable source ID,
- source/project name and canonical URL,
- verification date and evidence anchors,
- intended project purpose,
- exact data/resource/behavior classes available,
- license/provenance relevant to the intended use,
- Pokémon-IP caveat where applicable,
- update/version/pinning strategy,
- risks and known incompleteness,
- `ADOPT / ADAPT / REJECT / DEFER / REVISIT IN P6` decision,
- owning downstream contract or phase.

When a repository has both code/data and Pokémon images/audio, those rights boundaries must be recorded separately. A repository-level open-source license does not automatically relicense underlying Pokémon intellectual property.

## Source-role policy

No single community source is treated as universally authoritative.

Current P1 direction:

1. **Official Pokémon / Nintendo / rights-holder material** wins for official policy statements and setting/canon claims when such a source exists.
2. **PokéAPI static data** is the preferred structured baseline for broad species/form/game metadata because it exposes a stable, machine-readable REST-shaped dataset and schema.
3. **Pokémon Showdown** is a complementary source for generation-specific battle mechanics, learnset/legality behavior, and simulator-oriented move/ability semantics.
4. Conflicts between community sources are recorded and resolved intentionally in the owning design/data phase; fields must not be silently merged just because both sources expose similarly named values.
5. Production runtime must not depend on either remote service by default. Later import tooling should pin an upstream revision, normalize only approved fields into project-owned artifacts, validate them, then build runtime indexes/caches.

P1 intentionally does **not** define project-owned threat ratings, ecology tags, bond difficulty, local folklore, encounter rarity, or other derived gameplay semantics. Those belong to P4/P5 after P2/P3 constraints exist.

**Decision:** `ADAPT`

**Official API documentation:** https://pokeapi.co/docs/v2  
**Verified revision:** `2cda0b56a3a8ad2529d8aac73528225f96d2c848` (2026-08-11 updater regeneration)  
**Verified:** 2026-08-14

### Evidence anchors

- `api-data` README: static JSON copy of PokéAPI plus generated JSON Schema and an updater bot.
- `api-data/LICENSE.txt`: BSD 3-Clause text, copyright PokéAPI contributors.
- PokéAPI v2 docs: `pokemon`, `pokemon-species`, `move`, `generation`, `pokedex`, `version`, `version-group`, locations/encounters, abilities, evolution and related resource classes.

### Useful data classes

At reconnaissance depth this source can provide or link:

- Pokémon instances/varieties and species relationships,
- national/source identifiers and names,
- forms/varieties,
- base stats,
- type slots including historical type data,
- abilities including historical ability data,
- move associations with learn method / level / version-group detail,
- move metadata and historical values,
- generations, versions and version groups,
- Pokédex membership,
- evolution chains,
- encounter/location data,
- species metadata such as color, shape, growth rate, egg groups, capture rate and habitat where populated,
- sprite and cry references exposed by the API data model.

The existence of a field does not mean this project will import or expose it. P4 owns the canonical-source → project-domain mapping.

### License / provenance boundary

The `api-data` repository carries the BSD 3-Clause license from PokéAPI contributors. Treat that license as applying to rights the PokéAPI contributors can grant in the repository materials.

Pokémon names, game-derived facts, characters, designs, artwork, audio, trademarks and other franchise IP remain a separate rights question. Do not record `BSD-3-Clause = Pokémon IP licensed`.

Sprite/cry URLs or resource identifiers contained in structured data are **references**, not proof that the linked asset may be redistributed by this repository.

### Update and pinning strategy

- Upstream data is regenerated by an updater bot, so `master` is intentionally moving.
- Any importer must pin an exact commit or content hash rather than consuming `master` implicitly.
- The pinned revision and import timestamp must be stored with generated project artifacts.
- Updating the pin must be an explicit data update with validation/diff evidence, not an invisible runtime change.
- Runtime remote calls to `pokeapi.co` are rejected by default unless P7 later proves a concrete need.

### Risks / incompleteness

- Community-maintained extracted data, not a rights-holder canonical database.
- Some fields are version-sensitive and must retain generation/version-group context.
- Habitat and other descriptive fields may be null/incomplete or unsuitable as direct ecology rules.
- Flavor text is copyrighted game text and should not be copied wholesale into project-authored narrative merely because the API exposes it.
- Resource URLs cross into separate image/audio provenance concerns.

### Downstream ownership

- **P4:** decide the exact canonical fields imported and define project-owned derived Pokémon fields.
- **P6:** classify any referenced visual/audio resources separately.
- **P7:** implement pinned import, validation, generated artifacts and cached runtime indexes.

## SRC-DATA-002 — Pokémon Showdown server / Dex data

**Decision:** `ADAPT`

**Dex documentation:** https://github.com/smogon/pokemon-showdown/blob/master/sim/DEX.md

**Verified:** 2026-08-14

### Evidence anchors

- Repository README: Pokémon Showdown server is distributed under the MIT License and can be used as a JavaScript library for battle simulation / Pokédex data.
- `LICENSE`: MIT License, copyright 2011-2026 Guangcong Luo and contributors.
- `sim/DEX.md`: Dex exposes Pokémon, moves, items, abilities, natures and stats; `Dex.mod(...)` provides other-generation views.
- `sim/DEX.md` explicitly warns that Dex includes nonstandard data and that return values are not stabilized, recommending a pinned dependency version.
- Simulator validation/data files encode obtainability, move legality and generation-specific rules.

### Useful data / behavior classes

- species/form records,
- moves and detailed move behavior used by the simulator,
- abilities,
- items,
- natures and stats,
- generation-specific mods via `Dex.mod`,
- learnsets / move-source information,
- obtainability and legality behavior,
- generation-specific simulator mechanics useful for research or cross-checking.

### License / provenance boundary

The server repository is MIT-licensed as software and associated repository material to the extent contributors can license it.

That does not make Pokémon names, characters, designs, game text, audio, sprites or other underlying Pokémon IP MIT-licensed. Pokémon Showdown is also a community simulator, not an official Pokémon data authority.

Do not copy simulator implementation wholesale merely to obtain a few facts that can be normalized into a smaller project-owned contract.

### Update and pinning strategy

- Pin an exact Git commit or released package version for every extraction/analysis run.
- Do not depend on unversioned `master` at runtime.
- Preserve the upstream revision beside generated normalized artifacts.
- Explicitly filter/flag nonstandard content before ingesting anything into project-owned data.
- Because Dex return values are documented as unstable, importer code must validate expected shapes against the pinned revision rather than assuming an evergreen API contract.

### Source-selection rule

Use Showdown primarily where its specialization is valuable:

- generation-specific move/ability mechanics,
- learnset/legality evidence,
- differences across battle generations,
- simulator behavior that needs deterministic cross-checking.

Do **not** automatically prefer it over PokéAPI for every species metadata field. When both sources expose the same category, P4 must choose one authoritative project input or define a deliberate cross-check rule.

### Risks / incompleteness

- Includes CAP, custom, unreleased/past and other nonstandard data unless filtered.
- Simulator implementation may contain competitive/community interpretations or implementation details irrelevant to this text TRPG.
- Exact main-series fidelity is a research target of the simulator, but the repository is not an official Pokémon source.
- Pulling the full simulator into production would add unnecessary surface area if only normalized source data is needed.

### Downstream ownership

- **P4:** choose which move/ability/learnset/mechanics facts, if any, become canonical inputs for the project.
- **P7:** implement only the minimum pinned extraction/import path justified by P4; do not make the whole simulator a runtime dependency without evidence.

### Downstream ownership

- Underlying Pokémon audio rights are not granted merely by the repository's CC0 notice.
- Source-chain provenance spans multiple community projects.
- `latest` / `legacy` is a source-organization concept, not automatically the exact presentation model this game should expose.

- Which roster/forms actually need a cry and which `latest`/`legacy` source is coherent with presentation?
- What exact file hashes, attribution/provenance records, preprocessing and mobile audio budget apply?

### Downstream ownership

- **P4:** playable roster/form identity must be stable enough to define required cry keys.
- **P6:** decide whether cries are required/optional/deferred and establish the exact provenance/redistribution/resource budget contract.
- **P7:** implement only the P6-approved audio manifest/fetch/build/loading path.

## SRC-REF-001 — PokéRogue client, content, and resource organization

**Decision:** `ADAPT` as architectural/content/resource-organization reference only  
**Role:** reference for a mature browser Pokémon roguelite's separation of data, runtime systems, tests, locales and creative assets; not a source of project canon or a stack decision  
**Canonical client repository:** https://github.com/pagefaultgames/pokerogue  
**Canonical asset repository:** https://github.com/pagefaultgames/pokerogue-assets  
**Verified client revision:** `f0351391b1b75c7676dc234da82ad67ff5a3cfcd` (2026-08-13)  
**Verified asset revision:** `909b43612324622608023b3beb2f24f4ef159c1d` (2026-07-16 latest indexed commit at verification)  
**Verified:** 2026-08-14

### Evidence anchors

- Client README describes PokéRogue as a browser-based Pokémon fangame inspired by roguelites.
- Current `package.json` uses TypeScript, Vite, Phaser and Vitest, with explicit build/test/typecheck/data-generation scripts. This is evidence of one proven browser-game organization, not a requirement for this project.
- `.gitmodules` separates `assets` and `locales` into dedicated repositories/submodules instead of embedding every resource in the gameplay repository.
- `src/data/` contains many explicit game-data domains such as abilities, balance, dialogue, daily-seed data and biome-related data, while runtime concerns such as `src/audio/` have their own managers.
- The client and asset READMEs use REUSE/SPDX-style per-file licensing metadata rather than assuming one repository-wide license covers everything.
- The client README explicitly says assets without matching `REUSE.toml` licensing information should be considered to have **no licensing/copyright information**.
- The asset repository separates `audio/`, `images/`, `fonts/`, battle-animation data and other resource families, and its `REUSE.toml` marks selected logos as `LicenseRef-NO-REUSE`.

### Reference lessons worth adapting

The useful lessons are structural rather than code-level:

1. **Separate game logic/content from heavy creative assets.** A dedicated resource boundary makes provenance, updating and packaging easier to reason about.
2. **Treat provenance as file/class metadata, not as a blanket repository assumption.** A default-deny rule for unclassified assets is safer than inheriting a convenient top-level license label.
3. **Keep large game-content domains explicit.** PokéRogue's dedicated data directories show the value of named registries/contracts instead of burying content in scene/UI code.
4. **Separate runtime managers from declarative data.** For this project, P5/P7 should preserve a similar conceptual split even if the actual engine/framework is different.
5. **Make validation/tooling first-class.** Explicit test/typecheck/generation scripts are evidence that content-heavy games benefit from automated validation rather than manual inspection alone.
6. **Pin resource dependencies.** Submodule/revision-based resource boundaries are a useful reference for reproducibility, though this project may later choose manifests/build fetches instead of Git submodules.

### What this project must not copy by default

- PokéRogue's Phaser/Vite/TypeScript stack does **not** pre-decide P7 architecture.
- Its battle-loop, item economy, wave structure, balancing, Pokémon acquisition frequency and graphical presentation are project-specific assumptions, not authority for this text TRPG.
- Its source code is AGPL-v3.0-only unless otherwise noted; copying implementation creates license obligations and is unnecessary when the desired result is a project-owned contract.
- Its creative-asset repository is **not** a general asset library for this project. Pokémon-IP rights remain separate, some files carry specific exceptions, and unannotated asset files may have no licensing information.
- PokéRogue logos explicitly carry a no-reuse classification and must not be reused.

### License / provenance boundary

Current repository notices distinguish multiple categories:

- project source code: generally AGPL-v3.0-only unless otherwise noted,
- documentation: CC-BY-NC-SA-4.0,
- auto-generated / insignificant-originality files: CC0-1.0 where classified,
- licensable/applicable assets: generally CC-BY-NC-SA-4.0 unless otherwise noted,
- exceptions and no-reuse files: recorded through `REUSE.toml`,
- unclassified assets: explicitly not assumed to have usable licensing/copyright information.

None of those categories relicenses underlying Pokémon characters, designs, game-derived media or other franchise IP.

### Update and pinning strategy

- Treat the moving `beta` branch only as a discovery surface; record exact commit SHAs for every architectural/reference claim.
- If a later phase reuses a concrete organizational pattern, re-check the exact current file(s) rather than citing `beta` abstractly.
- Do not add PokéRogue as a runtime dependency merely to borrow organization ideas.
- If P6 studies its resource manifest/provenance approach in more detail, inspect the then-current `pokerogue-assets` revision and generated REUSE/SPDX bill of materials again.

### Risks / limits of comparison

- PokéRogue is a large graphical combat roguelite with very different interaction density from a mobile text adventure.
- Its mature architecture reflects years of project-specific evolution; copying its subsystem breadth would be over-engineering.
- A separate server repository exists in the PokéRogue ecosystem, but this project's current direction has no backend requirement; that architecture must not be inherited by analogy.
- Resource separation is a useful pattern, but Git submodules themselves are not yet selected for this project.

### Downstream ownership

- **P5:** may reuse the general lesson that authored content should live in explicit validated data contracts, not UI/scene code.
- **P6:** may adapt default-deny provenance classification and resource separation while creating this project's own manifest strategy.
- **P7:** independently choose the framework/build architecture from current primary documentation; PokéRogue remains comparative evidence only.

## SRC-CANON-001 — Pokémon Legends: Arceus official Hisui setting material

**Decision:** `ADAPT` as official setting precedent, not as a setting template  
**Role:** rights-holder primary evidence for how an official Pokémon title depicts a long-ago region where ordinary human–Pokémon coexistence is not yet normalized  
**Canonical story source:** https://legends.arceus.pokemon.com/en-ca/story/  
**Canonical gameplay source:** https://legends.arceus.pokemon.com/en-gb/gameplay/  
**Verified:** 2026-08-14

### Evidence anchors

- The official story page places Hisui in an age long ago and states that it was rare for people and Pokémon to live in close harmony.
- Jubilife Village is the Galaxy Expedition Team's base; its Survey Corps researches how Pokémon live, with separate Medical and Security Corps also named.
- The region contains distinct Pokémon ecosystems, clans and wardens who protect/revere special Pokémon and provide offerings.
- The gameplay page states that people living alongside Pokémon are rare and people leading Pokémon in battle are rarer still.
- Wild alpha Pokémon may chase and directly attack the player, demonstrating official precedent for Pokémon presenting personal danger outside formal trainer battles.

### What this evidence supports

This source **supports**, but does not fully define, D-003:

- a historical Pokémon setting can canonically make close human–Pokémon partnership uncommon,
- research/survey occupations and settlement-based expeditions fit official precedent better than importing generic fantasy classes by default,
- local cultures may revere, fear, serve or form exceptional bonds with particular Pokémon,

### Boundaries / risks

- Hisui is one specific official era/region, not proof that every ancient Pokémon society must work the same way.
- Do not copy Galaxy Team, clan, warden, noble, Pokédex-mission, dialogue or plot structures into the project merely because they are canonical precedent.
- P2 still owns the exact era, technology, terminology, settlement structure, religion/folklore intensity and severity of human–Pokémon conflict.
- Official web content is mutable; re-check the source when P2 uses a specific claim.

### Downstream ownership

- **P2:** use this as a constraint/precedent source while creating a distinct world bible.
- **P3:** may use survey/medicine/security-style social functions as evidence when deriving setting-native occupations, without cloning named Hisui institutions.
- **P4:** use the precedent that human–Pokémon relationship states can vary socially and individually rather than assuming modern trainer norms.

- The Nintendo Game Content Guidelines are expressly scoped to sharing gameplay footage/screenshots on video/image-sharing platforms; their FAQ states other uses of Nintendo IP are outside that guideline's scope.
- Nintendo's examples of content it may consider infringing include game software produced using Nintendo copyrighted material without authorization.
- Neither source establishes a blanket exception saying that a non-commercial fan game is permitted.

### Project policy derived from the evidence

- Keep the repository explicitly **unofficial, non-commercial and non-affiliated**, but never present those labels as permission or a license.
- A disclaimer can reduce confusion about affiliation; it does **not** authorize use of Pokémon IP.
- Do not cite Nintendo's streaming/image-sharing guidelines as permission to create or distribute this game; the guidelines explicitly cover a different use case.
- Do not turn convenient public Pokémon asset repositories into a claim of redistribution rights.
- Keep project-authored code/rules/text separable from third-party/Pokémon assets so removal/substitution remains technically possible.
- For public-repository and release decisions, prefer the minimum necessary third-party material and preserve provenance/default-deny handling established elsewhere in this registry.
